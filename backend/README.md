# SmritiCare Backend

## Private memory media storage

Memory photos and voice recordings are stored in the private S3 bucket. The existing `Memory.imageUrl` / `Memory.audioUrl` columns contain stable keys such as `memories/<userId>/<uuid>.jpg`, not public S3 URLs. Authenticated memory reads convert owner-scoped keys into presigned GET URLs that expire after five minutes. The upload API and `Memory` model remain unchanged; the migration adds a separate deletion outbox table.

New profile photos use the same private bucket and AWS SDK default credential chain. `User.profileImageUrl` stores a stable key such as `profiles/<userId>/<uuid>.jpg`; authenticated profile/auth responses and established caregiver-connection responses resolve that owner-scoped key into a five-minute presigned GET URL. Profile uploads keep the existing authenticated `POST /api/auth/profile-image` endpoint and `image` multipart field, enforce the 5 MiB limit, accept JPG/PNG/WEBP, and check the image signature matches the declared MIME type. Profile updates accept a managed key only for the current user and normalize a signed S3 URL only when it matches the configured bucket and exact supported S3 URL structure. Ordinary legacy HTTP(S) and `/uploads/...` references remain compatible. Uploads are written to S3 before the key is saved in MySQL. After a reported database write failure, the handler reads back the profile key and attempts deletion only if the uploaded object is confirmed unreferenced; if status is unknown, it retains the object.

If the upload and database update succeed but signed-URL generation fails, the upload endpoint returns the `PROFILE_IMAGE_SAVED_SIGNING_FAILED` code. The mobile client recognizes only that code and makes one authenticated `GET /api/auth/me` request with the same JWT. It verifies that the returned `user.id` matches the ID supplied by the active profile screen or saved with the current login/signup session, then accepts only a usable `user.profileImageUrl`. The multipart upload is not retried. A failed or timed-out refresh returns a safe error; unrelated upload failures do not trigger recovery. Profile-image signing failures use safe 500 responses; they are not reported as invalid credentials or profile validation errors. Caregiver invalid input maps to 400, authenticated role or ownership denial to 403, missing users/connections to 404, and unexpected internal failures to a generic 500. Missing/invalid JWT handling remains in the existing authentication middleware.

Offline `PROFILE` sync push also applies `profileImageUrl` using the authenticated sync user ID. An omitted property leaves the stored image unchanged, explicit `null` clears it, and non-null values pass through the same owner-aware normalization as profile updates. An owned signed S3 URL is stored as its stable object key; foreign S3 references fail that sync item without applying its other profile fields. Legacy HTTP(S) and `/uploads/...` references remain supported. This sync path does not delete old S3 objects and keeps the existing push-then-pull ordering and last-write-wins behavior. Caregiver controllers map typed invalid-input, authorization, and missing-resource errors to 400, 403, and 404; unexpected database/serialization errors use safe 500 messages. Successful response envelopes and `caregiverAccess` behavior are unchanged.

When `caregiverAccess` is disabled, the connected-patient list and new caregiver-to-patient connection response retain the patient's basic name and profile image but omit detailed profile fields. Whether profile images should remain visible under that setting is a product/privacy policy decision that still needs confirmation.

Configure the backend process environment:

| Variable | Value |
| --- | --- |
| `AWS_REGION` | `ap-south-1` |
| `S3_BUCKET_NAME` | `smriticcare-private-files-kashif-2026-2` |

These are documented application settings, not confirmation of the active deployed host or process environment. The repository's deployment descriptions are not sufficient to independently confirm the active platform, injected values, or attached IAM permissions.

The AWS SDK default credential provider chain is used. On production EC2, attach the `SmritiCareEC2S3Role` instance profile and grant it the required object actions for this bucket. Do not add access keys to source files or `.env`. Local development may use the developer's normal AWS SDK credential chain (for example, an AWS CLI profile); it does not require static application credentials.

Deploy by installing backend dependencies, setting the two environment variables in the process manager/EC2 environment, applying the committed migration with `npx prisma migrate deploy`, and running `npm run build` before restarting the backend through the normal deployment process. The migration creates `MemoryMediaDeletion`, a durable outbox used to retry S3 cleanup after a memory row is removed. Keep S3 Block Public Access enabled; the application only uses private object operations and short-lived signed reads.

The Express `/uploads` static route remains enabled for compatibility. Existing memory records containing local URLs and profile records containing legacy HTTP(S) or `/uploads/...` URLs continue to use those URLs. Existing files are not migrated or deleted; existing local profile and memory uploads remain under `backend/uploads` and must be retained while old records reference them. New profile uploads no longer write to local disk. Replacing a profile image does not automatically delete the previous S3 object, so old S3 profile objects require a separately reviewed cleanup process if retention policy calls for it. If a database write fails after upload and compensating deletion also fails, the new object may remain orphaned; the handler logs only a generic event, and profile media does not currently have a deletion outbox, retry worker, or configured alerting pipeline. If signing fails after the database update, the stable key remains saved and the mobile client attempts one authenticated profile refresh; it does not repeat the upload. If subsequent signing still fails, the UI receives a safe recovery error and the key remains available for later serialization attempts.

## Checks

From this directory, run `npx tsc --noEmit`, `npm run build`, and `npm test`. Profile recovery tests can be run from the repository root with `node src/services/profileImageUploadRecovery.test.cjs`. Backend tests cover owner-scoped memory/profile key validation, profile upload and sync behavior, rollback handling, legacy URL compatibility, caregiver status/error mapping, and memory deletion behavior. The mobile helper test covers recovery, identity matching, failure/timeout, and no-upload-retry behavior. These tests use mocks/helpers; real JWT verification, Prisma behavior, AWS S3 calls, deployed configuration, and IAM permissions require separate verification.

Completed media deletion outbox records are retained so duplicate direct DELETE requests can return idempotently after cleanup. Failed records are retried when the same direct deletion or offline sync DELETE is retried; there is no scheduled background worker in this backend.
